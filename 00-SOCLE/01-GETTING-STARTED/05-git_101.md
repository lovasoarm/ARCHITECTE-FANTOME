# Git : les premières commandes au moment utile

Temps de lecture indicatif : 5 à 7 min.

**N'ouvre cette ressource que lorsqu'une activité demande Git.** Git n'est pas nécessaire pour installer Node, commencer JavaScript, terminer Fundamentals ou commencer Problem Solving. Pour la première pratique, un dépôt local suffit ; GitHub, un compte distant et un projet personnel ne sont pas requis.

## 1. Vérifier ou installer Git

Dans un terminal, vérifie d'abord :

```bash
git --version
```

Si Git n'est pas reconnu, utilise les instructions officielles adaptées à ton système depuis [git-scm.com/downloads](https://git-scm.com/downloads). Sur Windows, l'installateur Git for Windows fournit Git Bash ; sur macOS et Linux, suis la méthode documentée pour ton système. Ferme puis rouvre le terminal après l'installation et relance `git --version`.

Cette installation n'est nécessaire qu'avant la première activité qui demande réellement Git. Elle ne bloque pas le premier exercice JavaScript.

## 2. Première passe : le cycle local

Le cycle le plus utile consiste à observer l'état, choisir précisément les fichiers, puis enregistrer un commit local :

```bash
git init
git status
git add notes.txt
git diff --cached
git commit -m "Ajoute les notes de départ"
git log --oneline
```

Dans cet exemple, `notes.txt` doit exister. Remplace ce nom par le fichier que tu as réellement créé. Préfère toujours `git add <fichier>` à `git add .` pendant les premières pratiques : tu contrôles ainsi exactement ce qui entre dans le commit.

Si `git commit` refuse de s’exécuter parce qu’aucune identité d’auteur n’est configurée, règle `user.name` et `user.email` **localement dans le dépôt d’exercice** avec `git config user.name "Apprenant AF"` et `git config user.email "apprenant@example.invalid"`. Ne configure pas une identité globale pour contourner ce message ; dans un vrai dépôt, utilise l’identité que ton équipe t’a indiquée.

Avant le premier `git add`, crée un `.gitignore` adapté et vérifie que les fichiers de configuration contenant des secrets ne sont pas suivis. Un commit local n'est pas une sauvegarde indépendante : il se trouve sur le même disque que ton projet.

## 3. Branches locales : lorsque l'activité les demande

```bash
git branch --show-current
git switch -c feature/notes
git switch <branche-initiale>
git merge feature/notes
```

Remplace `<branche-initiale>` par le nom réellement affiché par la première commande (`main`, `master` ou un autre nom). Ne suppose jamais le nom de la branche principale. Si `git switch` n’existe pas dans ta version, utilise `git checkout -b feature/notes` pour créer la branche puis `git checkout <branche-initiale>` pour revenir. La [pratique Git locale](../04-FUNDAMENTALS/50-git_core_minimini_projet.md) guide ce cycle dans un dossier jetable.

## 4. Dépôt distant : seulement si la consigne l'exige

Ces commandes servent à travailler avec un dépôt distant déjà identifié et autorisé :

```bash
git clone URL
git pull
git push
```

Elles ne font pas partie de la première pratique locale. N'utilise pas un dépôt personnel ou public pour un exercice qui ne le demande pas. Avant tout `push`, vérifie le dépôt distant, la branche, `git status` et `git diff` ; n'envoie aucun secret ni donnée personnelle.

## 5. Règles de sécurité débutant

- Un commit doit décrire une intention compréhensible.
- Vérifie ce qui sera enregistré avec `git status` et `git diff --cached`.
- Ne commite jamais un mot de passe, token, clé privée, fichier `.env` ou donnée personnelle.
- Ne lance pas `git push --force`, `git reset --hard` ou `git clean` dans les exercices débutants.
- Un dépôt local n'est pas une sauvegarde ; un dépôt distant ne doit être utilisé qu'avec les droits et consignes adaptés.

## Mission utile : première passe

Réalise la [pratique Git locale](../04-FUNDAMENTALS/50-git_core_minimini_projet.md) dans `scratch/git-drill/`. Crée deux commits, une branche, puis une fusion locale. Arrête-toi à un `git status` propre. N'utilise pas de dépôt distant.

**Preuve :** note les commandes réellement lancées, les deux messages de commit et le résultat final de `git status`. Ne joins pas de capture qui expose un chemin personnel ou un secret.

**Pourquoi :** la sélection explicite des fichiers et les commits rendent l'historique vérifiable.

**Quand :** avant la première activité de la route qui demande un dépôt, après avoir vérifié que Git est installé.

**Limites :** cette mission confirme seulement un cycle local ; elle ne prouve pas une collaboration distante, une revue de Pull Request ou une sauvegarde externe.

## Transfert produit différé : Kintana

> **Statut : différé et non bloquant.** Ce transfert n'est pas requis pour la première passe Git ; il attend une activité qui nomme explicitement Kintana et fournit un dépôt ainsi que des droits d'accès.

**Mission liée :** lorsque ces conditions sont réunies, prépare un clone propre, vérifie la branche et les consignes, puis propose un commit limité au besoin demandé. N'invente pas une exécution si le dépôt ou l'accès n'est pas disponible.

**Gate différée :** le diff est limité au besoin, aucun secret n'est suivi, le dépôt distant est le bon et la procédure est reproductible par un autre membre autorisé.

## Repères de décision

- **Pourquoi :** un historique local permet de comprendre et de retrouver une modification sans exiger un compte distant.
- **Quand l'utiliser / quand l'éviter :** utilise Git quand une activité demande de suivre des changements ; ne l'installe pas pour le premier exercice JavaScript.
- **Limites :** Git ne remplace ni une sauvegarde indépendante, ni une revue, ni une preuve de fonctionnement du logiciel.

## Mécanisme : dossier, index, commit

Le dossier de travail contient les fichiers édités. `git add` sélectionne les changements pour l'index (_staging_). `git commit` enregistre l'index dans l'historique local. Une branche est un nom qui pointe vers un commit ; une fusion réunit des historiques.

## Ancrage produit / terrain : Kintana

Kintana est un cas d'étude différé. Ne clone le dépôt que si une activité l'exige et que le dépôt, les accès et les consignes sont réellement fournis.

**À observer :** l'état du dépôt, les fichiers sélectionnés, le diff, le message du commit et le niveau de preuve. Une simulation locale ne prouve pas une livraison produit.
