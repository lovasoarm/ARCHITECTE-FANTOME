## GRIMOIRE DU REFACTORING

Le vocabulaire qui te permet de nommer un problème avant de le réparer.

| Terme                                 | Définition                                                                                        | Code                                                                                                                                                                     | Analogies                                                                                                                                               | Limite |
| ------------------------------------- | ------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------- | ------- |
| **Refactoring**                       | Changer la structure du code sans changer son comportement.                                       | `// avant : if/else en cascade` `// après : objet de lookup` `// le résultat retourné est identique (juste écrit plus proprement)`                                       | Naruto qui s'entraîne / Walking Dead qui réorganise le camp                                                                                             | « Naruto qui s'entraîne » se rejoue à l'identique, le code non ; sur Refactoring, un refactoring ne change pas le comportement observable, or ici l'image suppose qu'on améliore le produit. Verrouille le comportement par un test avant de toucher la structure. |
| **Code smell**                        | Signal que le code marche mais cache un problème de structure.                                    | `// 80 lignes dans une fonction` `// = smell : "long method"` `// (ça compile, ça pue quand même)`                                                                       | Breaking Bad (labo qui fuit) / Garo (armure qui craque)                                                                                                 | « Breaking Bad » tient tant que rien ne tombe en route ; sur Code smell, sans test de couverture préalable, le déplacement de code devient un pari. Verrouille le comportement par un test avant de toucher la structure. |
| **God class**                         | Une classe qui fait beaucoup trop de choses à la fois.                                            | `class CampManager {` ` fight() {}` ` cook() {}` ` saveToDisk() {}` `// trois métiers dans une seule classe` `}`                                                         | Naruto en mode tout-en-un / Walking Dead (chef qui fait tout)                                                                                           | « Naruto en mode tout-en-un » n'a ni facture ni horloge ; sur God class, le code mort n'est mort que jusqu'à preuve du contraire, souvent une réflexion dynamique. | **Feature envy**                      | Une fonction qui utilise plus les données d'un autre objet que les siennes.                       | `renderRating(match) {` ` return match.stats.goals * 4` `// la logique devrait vivre dans match, pas ici` `}`                                                            | Foot (coach qui joue à la place du joueur) / Naruto (clone qui fait le boulot du vrai)                                                                  | « Foot » a une frontière visible à l'oeil ; sur Feature envy, les métriques de qualité montent avant que la maintenabilité réelle change. | **Long method**                       | Fonction trop longue qui fait plusieurs choses sans le dire.                                      | `function processAll(data) {` ` // parse` ` // valide` ` // transforme` ` // log` `// 4 jobs en 1 fonction` `}`                                                          | Prison Break (plan trop long, trop de variables) / Naruto (mission S-rank sans checkpoint)                                                              | « Prison Break » tient tant que rien ne tombe en route ; sur Long method, un gros refactoring en un seul commit rend la bissection inutilisable. Vérifie l'usage réel avant de supprimer ce qui semble mort. |
| **Duplication**                       | Même logique copiée à plusieurs endroits, donc plusieurs sources de vérité.                       | `// règle écrite ici` `if (years >= 3) {}` `// et encore ici, copiée` `if (years >= 3) {}` `// si la règle change, fallait y penser 2 fois`                              | Country (refrain copié-collé mal) / Garo (deux Chevaliers avec le même ordre, jamais synchronisés)                                                      | « Country » raconte le cas nominal ; sur Duplication, la dette délibérée et la dette subie se ressemblent six mois plus tard dans le même fichier. | **SOLID**                             | 5 principes (SRP, OCP, LSP, ISP, DIP) pour garder un codebase qui évolue sans tout casser.        | `// S : une classe, une responsabilité` `// O : on étend sans réécrire` `// chaque lettre = une question à se poser`                                                     | Dragon Ball Z (5 guerriers, 5 rôles précis) / Walking Dead (groupe organisé vs groupe chaotique)                                                        | « Dragon Ball Z » se rejoue à l'identique, le code non ; sur SOLID, un renommage large casse les recherches, les liens et l'historique en même temps. Note la raison du changement dans le commit, pas seulement le quoi. |
| **OCP**                               | Open/Closed : on étend le comportement sans modifier le code existant.                            | `const jutsus = { rasengan: fn1 }` `jutsus.chidori = fn2` `// ajout sans toucher au moteur principal`                                                                    | Naruto (nouveau jutsu = nouvelle technique, pas une réécriture du ninja) / Trapsoul (nouvelle chanson = nouvelle piste, pas une réécriture de la radio) | « Naruto » se corrige toute seule quand elle dérape ; sur OCP, le code mort n'est mort que jusqu'à preuve du contraire, souvent une réflexion dynamique. Verrouille le comportement par un test avant de toucher la structure. |
| **LSP**                               | Liskov : une sous-classe doit pouvoir remplacer sa classe mère sans surprise.                     | `class Chevalier { fight() {} }` `class ChevalierBronze extends Chevalier {` ` fight() { return 'mode entraînement' }` `// respecte le contrat, comportement adapté` `}` | Garo (tout Chevalier doit pouvoir combattre, même le débutant) / Dragon Ball Z (un Saiyan reste un Saiyan, même faible)                                 | « Garo » tient tant que rien ne tombe en route ; sur LSP, sans test de couverture préalable, le déplacement de code devient un pari. Livre en petites étapes réversibles, chacune vérifiable. |

## OÙ LES ANALOGIES CASSENT (règle B.2)

Les analogies de ce grimoire simplifient : elles ne définissent pas. Une
closure **nest pas** un tiroir ; un event loop **nest pas** un carrousel ;
une pile **nest pas** une pile de crêpes. Chaque analogie sert à visualiser
un mécanisme ; elle cesse dès que tu veux raisonner sur la complexité, la
mémoire, la concurrence ou les cas limites. Reviens toujours à la définition
technique avant de coder, débugger ou expliquer à un pair. Une analogie
prise pour la réalité devient un obstacle épistémologique.
